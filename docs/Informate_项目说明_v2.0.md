## 1. 项目背景与缘起

### 1.1 市场观察

企业正在经历"AI 焦虑"——知道 AI 重要，但不知道怎么落地。市场现状存在结构性矛盾：

| 现状 | 问题 |
|:--|:--|
| 通用大模型（ChatGPT/DeepSeek 等） | 不接业务场景，员工用几天就不用了 |
| 大型定制 AI 方案 | 几十万起、周期长，大部分企业用不起 |
| 企业实际需要 | 不是 AI 技术，而是「能干活、懂行业、用得上」的 AI 助手 |

企业 AI 投入接受度集中在 ¥3,000-¥30,000/年，且大多无自研技术团队，需要开箱即用。

### 1.2 灵犀的教训（为什么冻结）

前一产品**灵犀（Lingxi）**经历了 v1.0-v4.0 迭代（2026-05 至 2026-06），走了"无 chat、完全由工作流推进"的路线，并融合了 SCRM 客户经营（8 个模块页面：Dashboard/广告来源/线索/客户/AI对话/知识库/分析/合规）。

**最终结论：灵犀的初步设计"使用页面和使用逻辑仍然较为复杂"。**

- 用户要学 8 个模块页面，每个模块有自己的表单/流程/状态
- 工作流驱动意味着"人要先理解流程，再操作系统"
- 对没有技术背景的企业员工，学习成本过高

### 1.3 Informate 的诞生

核心反思：**企业员工已经会聊天，不需要学系统。** 于是 Informate 采用完全不同的产品哲学：

> **把复杂度收进后端，前端永远只有一个对话窗口。**

- **灵犀逻辑**：人操作流程 → 流程调工具（用户学系统）
- **Informate 逻辑**：人对话 → AI 干活 → 产出物展示（用户只学对话）

本质上是**多 Agent 的聚合页面**——每个"场景"背后是一个独立的 AI agent（Hermes profile），但用户看到的只是"选一个场景，开始对话"。

## 2. 产品定位

### 2.1 一句话定义

> **Informate = 面向企业的 AI 能力平台。企业开通账号、充值积分，在对话里使用 AI 能力，产出物自动展示，所有能力按积分计费。**

### 2.2 产品形态（三栏布局）

```
┌────────────┬──────────────────────────┬─────────────────┐
│  左侧       │  中间                    │  右侧            │
│  场景列表   │  Chat 主窗口             │  产出物面板      │
│            │                          │                  │
│ 工作助手    │  用户: 帮我做一张          │  [图片预览]      │
│ 生成图片    │  夏季促销海报             │   ↓ 下载/发送    │
│ 生成视频    │                          │                  │
│ (按客户开通)│  AI: 好的，已生成          │                  │
└────────────┴──────────────────────────┴─────────────────┘
```

### 2.3 与灵犀的差异

| 维度 | 灵犀（冻结） | Informate（主产品） |
|:--|:--|:--|
| 驱动 | 无 chat，工作流驱动 | **Chat 驱动** |
| 前端 | 8 模块页面，用户学系统 | 1 个对话窗口，选场景即用 |
| 复杂度位置 | 前端（用户承担） | **后端（场景=agent 配置）** |
| 计费 | ¥1,000/角色一次性 | **开通费 + 积分消耗** |
| 可扩展性 | 模块堆叠 | 场景按需开放 |

### 2.4 目标客户

所有企业客户（不限行业、不限定规模）。行业差异通过"场景 × 行业"二维矩阵表达——**场景是通用的（工作助手/生图/生视频），行业是叠加的知识层**。

## 3. 产品设计（决策与推导）

### 3.1 前端交互（Q5/Q6/Q7）

| 决策项 | 决策 | 理由 |
|:--|:--|:--|
| 产出物面板 | 默认当前对话产出，可切历史 | 用户注意力聚焦当前任务 |
| 跨场景传递 | **手动**：点击"发送到其他场景"→ 投入对应场景对话 | 简单可靠；对话式 @引用 放二期 |
| 会话管理 | 场景下可新开对话（清上下文），后台保留历史 | 用户可控；记录可审计 |

**跨场景传递示例**：做图场景确认满意的图片 → 点击"发送到投放场景"→ 图片直接出现在投放场景的对话上下文里 → 投放 agent 基于这张图生成投放方案。

### 3.2 场景体系（Q2）

**MVP 场景（先做 3 个）**：
1. **工作助手** —— 通用文本对话（文档/表格/邮件/分析）
2. **生成图片** —— 营销图/海报/产品图（Seedream 5.0）
3. **生成视频** —— 营销短视频（H3 / Seedance）

**后续场景（按市场热度逐个开放）**：数据分析、投放和线索跟进、金牌销售、智能客服、内容运营等。

**场景开放逻辑**：客户按需求购买场景（¥500/场景/年），开通后该场景出现在左侧列表。**场景不是平台全给，是按客户需求开放**——这既是商业模式（卖场景），也是产品策略（客户只看到自己用的东西，界面天然简洁）。

### 3.3 场景包定义（场景 = 什么）

场景包是 Informate 的核心抽象，参考 **agency-agents-zh**（268 个角色，MIT 可商用，原生支持 Hermes）的定义格式：

```
场景包 =
  角色定义（frontmatter + 人设/使命/规则/交付物/流程/风格/指标）  ← 参考 agency-agents-zh
  + Hermes profile 运行时配置（模型/工具/skill/工作流/记忆）
  + 场景专属参数（积分单价 / 产出物类型 / 知识库绑定 / 工作流）
```

**关键认知**：agency-agents-zh 的 agent = 提示词角色（一份 system prompt）；Hermes profile = 完整运行时（模型+角色+工具+记忆+网关）。场景包是把两者 + 商业参数（积分/产出物）打包的标准结构。

### 3.4 每租户每场景独立 agent（Q3，本次设计最重要的决策）

**决策**：后端针对每个租户的每个场景配置**独立 agent**（独立 Hermes profile + 独立记忆/知识库）。

**为什么这么做？——不是为了隔离，是为了数据收集**：

> 用户原话："之所以要设计每租户每场景独立 agent 的方式，是我希望通过独立 agent 收集不同行业在这个场景下的共性需求，便于后期变更为行业垂直场景的 agent，这样有行业知识和沉淀的 agent 会比通用 agent 更有价值。"

即：**每个租户×场景的 agent 是一个"行业观察点"**。100 个医美客户的工作助手 agent，各自在真实业务中沉淀了医美行业的工作方式——汇总提炼后，就得到一个"懂医美行业的工作助手"垂类 agent，比通用版更有价值、更难被复制。

**租户信息模型**（Q15，延用灵犀客户注册表格式 + 补充）：
```
id / 公司名称 / 行业 / 子行业 / 状态(active/trial/paused/expired)
方案 / 已开通场景(roles) / 联系人 / 创建时间 / 到期时间
补充：企业规模 / 业务类型 / 目标市场
数据隔离边界（facts_boundary）：只读行业知识库，只写自己的租户 bank
```

**规模问题与演进（C 混合路线）**：
- 10 租户 × 5 场景 = 50 profile；100 租户 × 7 场景 = 700 profile（Hermes profile 是常驻进程，直接 700 个会资源爆炸）
- **路线**：初期（A）每租户每场景独立 profile 验证产品 → 规模化后（B）场景模板 profile + 租户数据隔离层（按需拉起）→ 混合演进（C）
- 初期产品跑通是第一目标，规模问题在设计阶段预留架构位（模板化创建）

## 4. 商业模式

### 4.1 计费模型（Q4）

```
客户 → 开通场景（¥500/场景/年）→ 充值积分（1元=10积分）→ 使用场景扣积分 → 用完再充
```

- 开通费按**年**收（不是一次性）——持续收入 + 客户留存压力
- 积分按**场景单价**扣费（不按 token）——B 端客户能理解"一张图 15 积分"，不能理解 token
- **积分规则**（Q9）：生成失败退积分（仅生成失败；效果不满意不退）；暂不设有效期；欠费冻结

### 4.2 定价推导（Q14：成本 → 售价 → 积分）

**毛利率口径**：实际 token/调用成本占售价 30%（售价 = 成本 ÷ 30%）。

**模型成本（2026-08-06 查证）**：
| 模型 | 用途 | 计价 |
|:--|:--|:--|
| deepseek-v4-flash | 文本 | 输入 1 元/M token，输出 2 元/M token |
| Seedream 5.0 | 生图 | 0.22 元/张（仅成功计费） |
| MiniMax H3 | 生视频 | 0.50 元/秒（768P）/ 0.80 元/秒（2K） |
| Seedance 2.0 | 生视频 | ≈1 元/秒（720p，按输出 token 计费） |

**典型消耗估算**：
- 工作助手一轮会话（≈5轮）：输入 10K token + 输出 1.5K token ≈ 0.075 元
- 生图一张：0.22 元
- 生视频一条（5s）：H3 768P = 2.50 元；Seedance 720p = 4.97 元

### 4.3 最终定价表

**报价策略：对外报价保守档，实际执行建议档（给客户让利打折）**

| 场景 | 计价单位 | 成本 | 对外报价（保守档） | 实际执行（建议档） |
|:--|:--|:--|:--|:--|
| 工作助手 | 1 会话（≈5轮） | 0.075 元 | 5 积分 | 4 积分 |
| 生成图片 | 1 张 | 0.22 元 | 15 积分 | 10 积分 |
| 生成视频标准档 | 1 条 5s（H3 768P） | 2.50 元 | 160 积分 | 120 积分 |
| 生成视频品质档 | 1 条 5s（Seedance 720p） | 4.97 元 | 330 积分 | 250 积分 |

**风险提示**：DeepSeek 峰谷 2 倍价待生效（保守档已覆盖）；H3 免费档并发仅 2 任务（批量生成需付费档）。

### 4.4 模型分工（Q11）

- 文本：deepseek-v4-flash
- 生图：火山方舟 **Seedream 5.0**（0.22 元/张）
- 生视频：MiniMax **H3** 768P（标准档，便宜/2K/编辑能力全球第1）+ 火山方舟 **Seedance 2.0** 720p（品质档，中文生态）**双轨可选**
- ⚠️ 关键发现：Seedance 与 H3 **都是视频模型，都不支持生图**——生图场景必须补充 Seedream（同平台统一接入）

## 5. 知识体系（核心护城河）

### 5.1 知识沉淀飞轮（Q13，延用灵犀设计之初方案）

灵犀在设计之初（讨论纪要 2.5/2.6/3.1/3.2 节）就完整设计了这个飞轮，逻辑与 Informate 完全一致：

```
客户使用 AI 干活
    ↓（记忆沉淀）
客户 Bank（customer_A_装修）积累知识
    ↓（每日聚合脚本）
提取 → 去重 → 脱敏
    ↓
写入行业 Bank（industry_装修）
    ↓
同行业其他客户加载行业知识库 → 获得更好的 AI 服务
```

**数据所有权设计**（关键）：
- 客户输入的业务数据 → **归客户**
- 服务过程中沉淀的行业知识（**脱敏后的术语/场景/模板**）→ **归平台**

**两阶段商业模型**：
| | 第一阶段（跑数据） | 第二阶段（变现） |
|:--|:--|:--|
| 目的 | 积累行业知识 | 利润最大化 |
| 定价 | 低价尝鲜 | 提价（搭载行业知识库的高级版） |
| 前提 | 无 | 每行业积累 50+ 客户知识 |
| 客户价值 | 花小钱用上 AI | 开箱即用，无需从零配 |

### 5.2 Informate 的适配（沉淀单元细化）

灵犀的沉淀单元是"客户 bank"；**Informate 细化为"租户 × 场景"的独立 agent 记忆**：

- 聚合维度从"行业"升级为"**行业 × 场景**"
- 例："医美行业的生图场景"沉淀的知识 ≠ "医美行业的客服场景"沉淀的知识
- 每个租户×场景的 agent 都配独立记忆（Hindsight bank），这就是 §3.4 的"行业观察点"

### 5.3 知识库三层结构（Q16）

| 层 | Hindsight bank | 内容 | 谁写 |
|:--|:--|:--|:--|
| 通用层 | informate-common | 平台级 FAQ/话术/SOP | 平台 |
| 行业层 | informate-industry_<行业> | 行业术语/FAQ/话术/法规库 | **飞轮聚合脚本（脱敏）** |
| 租户层 | informate-tenant_<租户> | 租户私有知识 | 租户自己的 agent |

**调研结论**（Q16）：不引入重型平台（Dify/RAGFlow/FastGPT 都不装）——底座 = Hindsight bank 体系（Postgres + 语义检索，原生支持 bank 隔离）；借鉴 RAGFlow 文档解析分层、MaxKB 管理界面形态、mem0 记忆提取生命周期；自研知识 schema（术语/FAQ/话术/SOP/法规库）+ 聚合脚本 + 管理 API。

### 5.4 Obsidian 人工层（Q17，双重积累）

- **Obsidian = 人工知识资产层**（`~/Desktop/Informate KB/`，git 管理）；Hindsight = 机器记忆层
- **分工**：AI 运行时读写 Hindsight（快但人不便读）；平台团队用 Obsidian 维护行业/通用知识的权威人读版
- **双向同步**：Hindsight 聚合 → flywheel/ 待审阅草稿 → 人工审阅编辑 → industries/ 权威版 → 回灌 Hindsight 行业 bank
- **三角色**：知识飞轮人工质检站（AI 提取质量把关）/ 行业知识资产库 / 交付物来源（客户知识手册导出）
- **红线**：租户私有数据绝不进 Obsidian（隐私）

### 5.5 护城河论述（竞品调研已验证，2026-08-06）

**护城河假设**：行业 × 场景的知识沉淀飞轮 → 具有行业场景知识的垂类 agent。

**竞品调研结论**（`artifacts/01_strategy/竞品调研报告.md`）：

1. **护城河成立，但比想象中窄**——"跨客户脱敏聚合 → 行业×场景知识库 → 回灌垂类 agent"这个闭环**目前没有竞品做透**（Coze 记忆库不跨客户聚合；小多 AI 只做电商客服单场景）；但数据飞轮不是自动成立的（数据质量/冷启动/竞品可复制），必须正视
2. **最大竞品是 Coze 企业版**（490 元/月起 + 积分 + 记忆库，字节资源），但它是"搭建型"平台——Informate 差异化在"**不用搭的 AI 工作台**"（替客户搭好场景 + 配好行业知识 + 开箱即用）
3. **护城河本质是运营不是技术**——行业运营深度 + 客户关系 + 数据积累 + 合规能力（M1 合规引擎是独特资产）
4. **加厚方向**：行业运营深度（每行业配运营维护 Obsidian 知识库）/ 合规能力产品化 / 交付服务标准化（开通即懂行）/ 垂类 agent 第二阶段单独售卖
5. **风险**：若 Coze 推出"行业场景包 + 跨客户知识聚合"，护城河被压缩——应对：速度（先跑出行业数据）+ 深度（行业运营）> 平台功能

## 6. 技术架构

### 6.1 整体架构（Q10）

```
客户浏览器（三栏 Web 页）
    ↓
自建 Node.js API 服务（服务端 Pipeline，2026-06-16 已验证端到端联通）
    ↓ 场景路由（每租户每场景独立 agent）
Hermes profile 引擎（模型 + 角色 + skill + 工作流 + 知识库）
    ↓ 工具层（复用 M1 资产改造）
合规检查 / 生图（Seedream）/ 生视频（H3/Seedance）/ LLM 调用
    ↓
Hindsight 记忆（租户/行业/通用 bank）+ Obsidian 人工层
```

### 6.2 关键设计

- **前端**：AI Studio 生成（已验证端到端联通），React 技术栈
- **后端**：Node.js API（鉴权/积分/场景路由/会话管理/任务代理）
- **Agent 引擎**：Hermes profile（每个场景一个 profile 配置，模型/角色/skill/工作流可差异化）
- **记忆**：Hindsight（bank 隔离天然支持三层知识结构）
- **积分**：预扣 + 结算 + 失败退分（原子性，参考灵犀 quota 的原子预留模式）

### 6.3 资产复用（Q12：M1 内容工厂拆件复用）

| 组件 | 复用方式 | 说明 |
|:--|:--|:--|
| compliance.py 合规引擎 + 4 行业规则包 + 违禁词库 + llm.py | ✅ 代码直接搬 | 完整交付已验收（458/458 绿），省 2-3 人天 |
| media.py 媒体生成 | ⚠️ 契约复用 | Seedance 客户端骨架/ImageToVideoParams 契约已有；真实接入是 M1.1 未完成工作（还是 mock）——Informate 补 Seedream/H3/Seedance 真实接入，估 2-3 人天 |
| orchestrator.py / api.py | ❌ 不搬 | 任务制编排 vs Chat 制架构差异大；借鉴幂等/重试/超时模式 |
| auth / quota / store | 🔧 模式复用 | token 哈希/原子预留/SQLite+WAL+幂等，升级为积分扣费 + 租户存储 |
