## 二、进入设计前必须钉死的 3 个底层逻辑

### 🔴 问题 1（架构）：进程池的"租户上下文污染"隐患

- **风险**：长生命周期 worker 注入租户上下文时，上一个租户的残留状态可能污染下一个租户
- **两个方案**：
  - A. **无状态 Worker + 每次全量注入**（隔离最高，中等复杂度）
  - B. 租户亲和路由 Sticky Session（有状态但绑定，低复杂度）
- **Codex 建议**：MVP 选 **方案 A（无状态）**——多租户 Bug 几乎为零，对稳定性至关重要

### 🟡 问题 2（数据）：二级行业的"检索权重"必须提前定义

- **风险**：Q25 说"按权重合并"但没定义公式
- **Codex 建议**：MVP 用**硬编码优先级**（不要向量加权融合）：
  ```
  P1: 租户私有 bank（精确匹配二级行业）
  P2: 行业 bank 中 sub_industry = 租户二级行业
  P3: 行业 bank 中 sub_industry = null（通用）
  P4: 通用 bank
  ```
- Hindsight bank 检索本质是**结构化分层读取**，不是语义搜索混合排序

### 🟢 问题 3（业务）："首单免部署费"与"¥500 一次性"的切换时机 + 试用限制矩阵

- 首单免部署费是**永久政策**还是**上线前 3 个月促销**？
- 试用限制必须量化（否则开发反复问）：
  - 生图带水印 → 水印位置/样式固定
  - 会话次数限制 → **初期 20 次/租户**
  - 跨场景传递 → 建议试用期**禁用**

## 三、定价死穴：DeepSeek 最新价格依然悬空

- v3.0 定价表基于老价格（输入 1 元/M、输出 2 元/M），DeepSeek 若大幅涨价 → 工作助手毛利从 30% 归零甚至倒挂
- **必须立即执行**：
  1. 登录 DeepSeek 控制台拉取最新定价（含峰谷实际价格）
  2. 按高峰价 + 预估涨幅重算工作助手单会话成本
  3. 若新成本 > 执行价（8 积分=0.8 元）的 50%（即 >0.4 元）→ **必须再次上调定价** 或修改"会话"定义（5 轮→3 轮）
- **保险策略**：积分单价设计为**管理后台可配置变量**，不硬编码；上游涨价后台一键调价 + 公告
