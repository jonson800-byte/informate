## 0. 文档速览（30 秒版）

- **架构一句话**：浏览器（三栏工作台）→ Node.js API（鉴权/会话/积分/任务编排）→ BullMQ（异步 Job）→ Hermes api_server（场景 Worker 池，无状态全量注入）→ Hindsight（三层 bank 记忆）+ DeepSeek（文本）/ 火山方舟 Seedream 5.0（生图）。
- **租户隔离**：`bank_id_template: 'informate-tenant-{user}-{profile}'`（FR-207 连字符版定稿）；`{user}`=租户 ID，由 Node.js 后端经 **X-Hermes-User-Id 请求头**可信注入（Hermes api_server 源码改造，方案 a，约 15 行）。
- **计费**：会话型 15 积分/会话（含 20 轮）+ 超轮 1 积分/轮 + 上限 50 轮（第 51 轮拦截）；生图型对外 20 / 实扣 15 积分/张；1 元 = 10 积分；两阶段积分事务（冻结 → 成功扣减 / 失败原子解冻），BullMQ 承载。
- **Worker 池**：每场景 1 个 Hermes profile（api_server 进程），池大小按并发会话 5-10 建模；热 Worker 首 token ≤ 2s，冷启动 ≤ 30s（前端占位「正在准备」）；闲置 15 分钟销毁租户绑定（进程回池复用）。
- **管理后台**：MVP 必选，6 模块（租户 / 场景部署 / 积分 / 价格配置 / 会话审计 / 员工限额）+ 数据导出 + 运营看板(P1)。
- **关键前置（P0 阻塞）**：Hermes api_server 源码改造（X-Hermes-User-Id）必须先于集成联调完成，隔离测试用例固化回归。

## 一、总体架构

### 1.1 设计原则

| # | 原则 | 落地 |
|:--|:--|:--|
| P1 | 无状态 Worker + 每次请求全量注入（NFR-06/08、Q18） | Worker 不持有租户状态；系统提示 = 角色定义 + 场景包 + 行业叠加层；记忆 = bank 动态解析；会话历史由 Node.js 数据库管理，每请求携带完整消息数组 |
| P2 | 租户×场景独立记忆（FR-207） | bank_id_template 动态解析，{user}=租户 ID 后端可信注入，{profile}=场景名 |
| P3 | 计费与业务解耦（Q20、Schema §3.6） | 积分冻结/扣减/解冻由平台积分管线（BullMQ）执行，场景包 workflow 只描述业务动作序列 |
| P4 | 一切可配置、前端零硬编码（FR-704、UIUX §6） | 单价/含轮数/上限/提示文案/充值档位全部读 price_config + 场景包元数据 |
| P5 | 审计全量留痕（NFR-17） | 登录/操作/合规拦截/跨场景传递/后台配置变更 → audit_log |
| P6 | 异步不阻塞对话（NFR-15、FR-303） | 生图为异步 Job；SSE 流式对话；任务状态可见 |

| 网关层 | Node.js API 网关 | JWT 鉴权、租户上下文（tenant_id/user_id/role）、RBAC、限流、统一错误 | 业务表带 tenant_id；越权 403（NFR-07） |
| 业务层 | 租户/场景/会话/产出物/后台服务 | 见 §2 各模块 | 状态机见 PRD §3.3/§4.3 |

### 1.4 核心数据流

**数据流 1：行业工作助手会话（会话级计费）**

```
前端 POST /conversations/{id}/messages
 → 网关鉴权 + 租户状态校验（trial 查次数 / active 查余额 ≥ 冻结额 / paused·expired 拒绝）
 → 轮次校验：turns ≥ 50 → 拦截（第 51 轮，提示新开对话）；turns ≥ 20 → 增量冻结 1 积分
 → 会话冻结：**POST /conversations 创建即冻结 15**（credit_txn: freeze, ref=conversation；未使用 30 分钟自动释放）
 → 组装请求：messages=完整历史+新消息；X-Hermes-User-Id=租户ID；X-Hermes-Session-Id=会话ID
 → Worker 池取热 Worker → Hermes api_server 流式回复（SSE 透传前端）
 → 流式结束（该轮完成）：回复过合规检查（medical 规则包，命中自动修正）→ 超轮扣减 1
    （credit_txn: settle）→ **message 落库与扣减在同一事务/幂等重放**（防崩溃窗口扣费成功但消息丢失）→ turns+1
    → 第 20 轮末追加系统提示「已用满含轮」；turns=50 时提示上限
 → 会话结束/新开对话：冻结余额结算（未扣部分解冻）
```

**数据流 2：生图（任务级计费）**

```
前端在 Chat 中描述图片需求
 → Hermes Agent（generate_image 场景）意图解析 + 租户品牌记忆加载
 → 前置合规检查（违禁提示词/医美前后对比 → 拦截，不产生扣费）
 → Agent 产出结构化生图请求（tool call：prompt/negative_prompt/aspect_ratio/...）
 → Node.js 捕获 → POST /image-tasks：冻结 15 积分 → BullMQ 入队（并发按供应商配置，超限排队）
 → 生图 Worker 调火山方舟 Seedream 5.0（异步任务 + 回调/轮询）
 → 成功：webhook 幂等 → 扣减 15（settle）→ 图片+元数据 Payload 入 artifact
 → 失败/超时：原子解冻 15（unfreeze）→ 任务 failed + 原因 → 前端重试
 → 产出物入右栏（预览/下载/重新生成/发送到其他场景）
```

**数据流 3：充值 → 转正式**

```
主账号选档位（100/500/2000 元）→ POST /recharge/orders 建单
 → 支付渠道回调（对公转账人工确认）→ 幂等入账：到账 = 金额×10 × (1+赠比)
 → credit_txn: recharge → balance 刷新 → tenant.status: trial→active（水印移除/次数解锁/传递开放）
 → 员工限额与余额联动：先判租户余额，再判员工限额，提示语区分（PRD §4.4）
 → 部署费：MVP 阶段**免收（首单引流 D3）**——trial→active 仅由充值触发；¥500/场景一次性部署费作为正式收费项在 T15 上线准备中定稿（含收付/发票/转 active 判定），并显式映射 FR-606（积分无有效期）
```

### 1.5 技术选型

| 层 | 选型 | 理由 |
|:--|:--|:--|
| 后端 | Node.js 20 LTS + TypeScript + Fastify | 与 BullMQ 同栈；灵犀 M1 模式复用（auth/quota/store 思路） |
| 数据库 | SQLite + WAL（MVP）→ PostgreSQL（规模化） | 单机打样 5-10 并发足够；schema 带 tenant_id 预留迁移 |

| 前端 | React 18 + Vite + TypeScript + SSE | 流式渲染；三栏布局；零硬编码由场景包元数据驱动 |
| Agent 引擎 | Hermes api_server（每场景 1 profile）+ Hindsight(9177) | Q10/Q18 定稿；bank_id_template 原生支持 |

## 二、模块设计

> 每个模块给出：职责 / 关键流程 / 接口要点 / PRD FR 映射。

### 2.1 租户与账号

**职责**：租户全生命周期（trial/active/paused/expired 状态机）、主账号与员工子账号、登录鉴权、冻结提示页数据。

**关键流程**：
1. 开户（FR-101）：运营后台创建租户 → 生成租户 ID（uuid）与主账号（owner，初始密码随机）→ 默认 `trial`（FR-501，试用会话 20 次 + 生图带水印）。
2. 登录分流（FR-102/106）：登录成功后按租户状态分流——trial/active → 工作台；paused/expired → 冻结提示页（原因 + 联系运营；expired 额外提供数据导出入口）。
3. 员工子账号（FR-105）：主账号创建/停用；员工登录后仅见使用界面（充值/管理入口隐藏）。
4. 欠费冻结（FR-605）：active 租户余额 < 最低冻结额（会话 10 / 生图 15，取场景最小值 **10**）→ 自动转 paused；充值后 1 分钟内恢复 active。
5. 试用额度（FR-501/502）：trial 租户按次数计（不查余额）；会话第 21 次发起被拦截并引导转正式。

**接口要点**：
- `POST /api/v1/auth/login` → JWT + 用户信息 + 租户状态 + 余额快照 + 试用剩余次数。
- 所有业务接口经 `tenant-context` 中间件：从 JWT 解析 tenant_id/user_id/role 注入请求上下文；越权 403。
- 密码哈希复用 M1 auth 模式（bcrypt/scrypt + 盐），绝不落明文。

**FR 映射**：FR-101/102/103/105/106/501/502/503/504/505/605、NFR-07/09。

### 2.2 场景部署

**职责**：场景包加载与校验、按租户部署（行业知识叠加层绑定）、display_name 渲染、左栏场景列表下发。

**关键流程**：
1. 场景包入库：YAML → JSON Schema 硬校验（15 顶层字段，additionalProperties:false）→ 平台业务校验 B1-B10（`validateScenarioPackage`）→ 存 scenario 表 + 版本化。
2. 部署（FR-702）：运营后台按租户开通场景 → 校验：① 行业知识叠加层就绪（`informate-industry_<行业>` bank 有种子知识，否则拒绝部署并提示补齐）；② 医美行业强制 compliance.enabled=true 且含 medical（B9）；③ 生成图片场景可选 target_scenario 有效性。
3. display_name 渲染（Q28）：`display_name_template`（如 `{industry}行业工作助手`）按租户一级行业渲染 → 左栏场景名（医美 → 「医美行业工作助手」）；缺省直接用 `name`。渲染结果缓存到 scenario_deployment.display_name，行业变更时重渲染。
4. 场景列表（FR-103）：`GET /workspace` 只返回已部署且 status=active 的场景（未部署/暂停不出现），附带场景包元数据（emoji/color/suggestions/单价显示/合规提示条文案）。
5. 检索优先级绑定（FR-203，部署时硬编码）：P1 租户私有 bank → P2 行业 bank 中 `sub_industry`=租户二级行业 → P3 行业 bank 通用条目 → P4 通用 bank。

**接口要点**：
- `GET /api/v1/workspace`：左栏数据源（场景列表 + 余额 + 租户状态 + 试用剩余）。
- `GET /api/v1/scenarios/{id}/meta`：场景包元数据（空态建议 chips、计费显示、合规提示条文案）。
- 管理后台 `POST /admin/tenants/{id}/deployments`：部署/关闭场景。

**FR 映射**：FR-103/202/203/207/702、Q25/Q28、Schema §3.5/§4.4（B6-B9）。

### 2.3 Chat 会话（行业工作助手）

**职责**：多轮流式对话、api_server 调用、轮次计费（含轮/超轮/50 轮拦截）、上下文管理、租户记忆、会话可用性检查。

**关键流程**：
1. 新会话（FR-104）：`POST /conversations {scenario_id}` → 可用性检查（FR-208）→ 首轮冻结 15 积分 → 返回 conversation_id。
2. 发消息：`POST /conversations/{id}/messages` → 校验（见 §1.4 数据流 1）→ 调 Hermes api_server（流式 SSE）→ 前端逐 token 渲染。
3. 轮次计费（FR-205，PRD §4.2/§4.3）：1 轮 = 用户 1 条消息 + Agent 完整回复（流式结束即完成，工具调用计入该轮）；20 轮内不追加扣费；第 21 轮起每轮发起前**增量冻结 1**、回复完成**扣减 1**；第 50 轮正常完成并计费；**第 51 轮发送被拦截**（不冻结不扣费）提示「建议新开对话」；中途余额不足（<1）当前轮允许完成、下轮前冻结失败提示充值。
4. 上下文管理（FR-206）：Node.js 维护完整消息历史，超长由 Hermes 原生压缩/截断。
5. 租户记忆（FR-207）：Hindsight bank 由 `bank_id_template` 动态解析；会话记忆自动写入租户 bank（同租户不同场景隔离）。
6. 合规（FR-204/209）：回复完整文本过 M1 合规引擎；营销文案类产出自动附带发布审查提示（后台可配文案）。

**接口要点**：
- `POST /conversations`、`POST /conversations/{id}/messages`（SSE 响应）、`GET /conversations/{id}/messages`、`POST /conversations/{id}/end`（结算解冻）、`GET /conversations?scenario_id=`。
- SSE 事件契约：`{event:"delta", data:{text}}` / `{event:"round_complete", data:{turns, credit_charged}}` / `{event:"round_hint", data:{type:"included_used|extra_round|limit_50|low_balance"}}` / `{event:"error"}`。
- 会话结束/新开对话 → `billing_state: frozen→settled`，冻结余额结算（未扣部分解冻）。

**FR 映射**：FR-201/104/205/206/207/208/209/602/603、PRD §4.2/§4.3、NFR-13/14。

### 2.4 生图（生成图片场景）

**职责**：对话内生图（FR-301）、异步任务（FR-303）、两阶段积分（FR-304/604）、并发控制（FR-305）、前置合规（FR-306/307）、产出物面板（FR-302/401/402/403）。

**关键流程**：
1. 触发：Chat 描述图片需求 → Agent 意图解析 + 租户品牌视觉记忆加载 → 前置合规检查（违禁词/医美前后对比/医疗效果承诺 → 拦截并说明，**不产生扣费**）。
2. Prompt 扩写：Agent 输出结构化 tool call（`seedream_v5_generator` JSON 契约：prompt/negative_prompt/aspect_ratio/image_resolution/ref_image_url/product_fidelity）。
3. 提交任务：Node.js 捕获 → `POST /image-tasks` → 冻结 15 → BullMQ 入队 → 任务状态（排队中/生成中/成功/失败）可见。
4. 执行：生图 Worker 调 Seedream 5.0（异步提交 + 回调/轮询）；供应商并发上限（参考 H3 免费档 2 并发口径，Seedream 按火山方舟实际配置）——超限**排队不报错**（FR-305）。
5. 结算：成功 → webhook 幂等扣减 15 → 图片落存储 → artifact 入右栏（**元数据 Payload：prompt/aspect_ratio/style_tags/target_product/audience/selling_points/seedream_params**——audience=受众人群、selling_points=产品卖点，随跨场景传递投递 AC-403/G4 定稿）；失败/超时 → 原子解冻 15 + 失败原因 + 重试（FR-304）。**MVP 图片存储：本地磁盘目录 `./data/artifacts/` + `GET /artifacts/{id}/download` 文件流（FR-402）；文件命名 `{artifact_id}.{ext}` 与 artifact 表 uuid 对应；备份随 DB 每日快照；生产化后迁对象存储/CDN（生成图片.yaml 的 cdn.informate.ai 为远期 url_template）**
6. 产出物操作：预览/下载原图/重新生成（按次计费，重走冻结-结算）/发送到其他场景（FR-403，目标场景已部署且租户 active，试用期禁用）。
7. AI 标识：图片文件后端合成（试用水印可移除 vs 合规 AI 标识永久保留，独立处理，FR-504/NFR-01）。

**接口要点**：
- `POST /api/v1/image-tasks`、`GET /api/v1/image-tasks/{id}`（状态轮询）、`POST /api/v1/artifacts/{id}/regenerate`、`POST /api/v1/artifacts/{id}/transfer`。
- BullMQ Job 数据：`{tenant_id, user_id, conversation_id, task_id, prompt, params, frozen_credit:15, provider, idempotency_key}`；供应商 webhook 校验签名 + 幂等键唯一约束。

**FR 映射**：FR-301~307/401/402/403/404/405、NFR-01/15/16。

### 2.5 积分管线

**职责**：积分账本（balance + credit_txn）、两阶段冻结/结算/解冻状态机（PRD §4.3）、充值阶梯包（FR-601）、消费明细（FR-602/603）、欠费冻结（FR-605）、员工限额（FR-706）、价格配置（FR-704）。

**关键流程**：
1. 充值（FR-601）：档位 100 元→1100 积分（赠10%）/ 500 元→6000（赠20%）/ 2000 元→25000（赠25%），档位与赠比后台可配；支付成功即时到账（对公转账人工确认回调）；1 元 = 10 积分。
2. 冻结/结算/解冻（FR-604，PRD §4.3）：
   - 任务级（生图）：提交冻结 15 → 成功 webhook 扣减 15（终态）/ 失败/取消/超时原子解冻 15（终态）。
   - 会话级（工作助手）：首轮冻结 15 → 20 轮内含轮 → 21 轮起每轮增量冻结 1 → 回复完成扣减 1 → 会话结束结算（未扣解冻）→ 51 轮拦截 → 余额不足当前轮完成、下轮前冻结并引导充值。
   - 兜底（仅限任务级冻结，禁止对活跃会话级冻结按时长解冻）：后台每 5 分钟扫描**任务级**冻结——按 ref 状态判定（生图任务非终态且超时 → 解冻并置任务失败；解冻前核对上游任务状态，若上游实际成功则不解冻、走正常扣减）；会话级冻结仅在会话结束/新开对话时结算释放（未使用会话：创建后 N 分钟无任何消息 → 自动结算释放，N=30 可配）；**解冻后若上游图片回调迟到 → 图片照常交付但积分不重复扣（补偿规则：该 artifact 标记 "already_unfrozen"，流水留痕）**
3. 幂等：所有 webhook 回调带 `idempotency_key`，credit_txn 唯一约束，重复回调不重复扣（NFR-16）。
4. 并发安全：余额更新用 SQLite 事务 + 条件更新 `UPDATE tenant SET balance=balance-? WHERE balance>=?`；并发提交生图按提交顺序冻结，余额不足任务进入失败态并提示（PRD §4.4 异常对照）。
5. 员工限额（FR-706）：`user.credit_limit`（可配周期，如每日）；判定顺序：**先判租户余额，再判员工限额**，提示语区分原因。
6. 价格配置（FR-704）：price_config 表存 key→value（会话含轮数/会话单价/超轮单价/生图单价/试用次数/合规提示文案/充值档位），改动即时生效并留审计；场景包价格为出厂默认（B10）。

**接口要点**：
- `GET /api/v1/credits/balance`、`GET /api/v1/credits/txns`（分页：时间/场景/类型/积分/ref_id）、`GET /api/v1/recharge/packages`、`POST /api/v1/recharge/orders`、`POST /api/v1/recharge/callback`（内部）。
- 积分流水类型：`recharge/freeze/settle/unfreeze/adjust`（对齐 PRD §7.5 credit_txn.type）。

**FR 映射**：FR-601~606/704/706、PRD §4.2/§4.3/§4.4、NFR-16。

### 2.7 合规（M1 引擎复用）

**职责**：文本输出合规（FR-204）、营销文案发布审查提示（FR-209）、生图前置合规（FR-306）、医美生图限制（FR-307）、AI 标识（NFR-01）、Opt-in 知识共享（NFR-02）。

**关键流程**：
1. 引擎形态：M1 `compliance.py` 违禁词引擎 + 规则包（general/medical/education/finance/food_health）+ toolgood_words 违禁词库 + LLM 兜底 + 自动修正——**拆件复用**（Q12），封装为独立 Python 合规服务（FastAPI，:9100），Node.js HTTP 调用。
2. 文本合规（FR-204）：Agent 流式回复完整文本 → 合规检查（medical 规则包：广告法绝对化用语/医疗广告审查/前后对比禁令/违禁词库）→ 命中自动修正或拦截并提示 → 标注 `compliance_passed`。
3. 发布审查提示（FR-209）：行业工作助手生成营销文案时自动附带「需人工审核且取得《医疗广告审查证明》后方可投放」（文案后台可配 FR-704）；生图场景提示「生成图片不得用于前后对比等医疗效果承诺」。
4. 生图前置合规（FR-306/307）：生成请求先过合规检查，违禁提示词拦截并说明、不产生扣费；medical 拦截前后对比图、医疗效果承诺类图。
5. AI 标识（NFR-01/FR-504）：图片文件后端合成标识（右下角水印 + 元数据 `ai_label=true`），**永久保留**；试用营销水印独立元素，转正式后新产出物移除。
6. Opt-in（NFR-02/03）：服务协议明示或「加入知识共享计划享积分打折」显式开关；脱敏提取仅作 Draft 进 Obsidian flywheel/，未经人工批准严禁回灌行业 bank。

**接口要点**：合规服务 `POST /check {text|image_prompt, rule_packs:[general,medical]}` → `{passed, fixes[], blocked, reason}`；后端在回复落库前/生图提交前调用。

**FR 映射**：FR-204/209/306/307、NFR-01/02/03/04/05/11/12、Q19。

**数据使用与删除（NFR-05/11/12 落点）**：
- 训练关闭开关：租户可在后台/条款中关闭「数据用于知识共享计划」（Opt-in，Q19）——关闭后该租户对话不进入行业聚合管道
- 数据所有权：客户业务数据归客户（租户 bank）；脱敏行业知识归平台（Q13）；Obsidian 红线：租户私有数据绝不进 Obsidian
- 删除流程：租户删除/退出时，租户 bank 数据保留期（默认 30 天可配）后清除；会话审计按法规保留；提供数据导出（FR-505/admin export）
- 商业秘密保护：知识飞轮聚合前人工审核关卡（NFR-03），未批准条目不得回灌行业 bank（Gemini Q19 采纳）

```sql
CREATE TABLE tenant (
```

```python
def _parse_user_id_header(self, request):
    """解析 X-Hermes-User-Id。租户 ID 由可信后端注入；
    仿 _parse_session_key_header：拒绝 \r\n\x00，长度 ≤ 256。"""
    value = request.headers.get("X-Hermes-User-Id", "")
    if not value:
        return "", None
    if "\r" in value or "\n" in value or "\x00" in value:
        return "", _openai_error("invalid user id", code="invalid_user_id")
    if len(value) > 256:
        return "", _openai_error("user id too long", code="invalid_user_id")
    return value, None
```

### 5.4 Worker 池设计（无状态 + 按需拉起 + 闲置回收）

**形态**：每场景一个 **api_server 进程池**（每场景 profile 派生，**池大小按进程数**：min=2 热备 / max=5，端口按序分配 **8642+i**；多进程承载并发会话 5-10，单进程内多会话复用——G1 定稿：**每场景多进程 + 显式端口分配**，废弃"每场景 1 进程"表述）。Node.js 侧 WorkerPool 模块管理。

```
WorkerPool（Node.js，每场景一个池）
├── 池大小：按进程数建模 min=2 热备 / max=5（可配，对应并发会话 5-10 由 2-5 个进程分担，NFR-14）
├── 进程：spawn `hermes -p informate-scene-<id> gateway`（端口 8642+i 显式分配，进程内多会话复用）
├── 路由：会话请求 → least-loaded 热 Worker（首 token ≤ 2s）
├── 冷启动：池满 → 拉起新进程（≤40s 就绪，前端占位「正在准备你的行业助手…」，不空白等待 NFR-13；实测 20-40s，按 40s 定 SLA）；超上限 → **挂起 SSE 连接排队**等待 Worker 释放（上限可配；与生图 BullMQ Job 队列分开——Chat 是同步流式，非异步 Job）
├── 租户绑定：进程本身无租户状态（无状态注入）；会话→Worker 亲和映射存 Node.js 内存；**亲和丢失恢复**：Node 重启或进程回池复用后，同 X-Hermes-Session-Id 请求若路由到无该会话上下文的 Worker → 检测后自动重试路由（最多 2 次）或返回「会话上下文已过期，请重发本条消息」提示，不静默丢消息（ISO-05 补进程重启变体用例）
├── 闲置回收：某租户 15 分钟无会话 → 销毁租户绑定（清亲和映射 + Hermes 会话状态，进程回池复用，不销毁进程 NFR-08）
├── 缩容：整池空闲 15 分钟 → kill 多余进程（保留 min）
└── 健康：每 30s /health 轮询；连续 3 次失败 → 重启；kill -9 兜底
```

**关键点**：
- **无状态注入**：每次请求携带完整 messages 历史 + 系统提示（角色定义 + 场景包 + 行业叠加层说明），用后即弃——杜绝跨租户状态污染（NFR-06"模型会话缓存/工具状态/连接凭据全部重置"）。
- **X-Hermes-Session-Id** = Informate conversation_id（uuid），保证 Hermes 侧会话连续性作用域独立（防同提示词指纹派生撞 session，api_server-userid-plumbing §2 第 1 行）。
- **多场景扩展**：新场景 = 新 profile + 新池（水平扩展无需改核心代码）。
- **api_server 地址**：Node.js 直连 127.0.0.1:864x，`API_SERVER_KEY` 放服务端环境变量。
